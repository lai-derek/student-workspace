# Build Targeted Cover Letter

Work in the student workspace and follow `WORKSPACE.md`. Use this skill when the user requests a letter or a requested application packet requires one. A resume-only request does not authorize drafting an optional letter. Automatic skill discovery remains enabled for relevant cover-letter requests. Creating this skill or reviewing job fit is not a request to draft a letter.

## Coordinate the application packet

Use [build-targeted-resume](../build-targeted-resume/SKILL.md) for a complete resume. A cover letter can be created without rebuilding it. Reuse the current application resume, dated posting snapshot, evidence matrix, source notes, accepted wording, and established gaps. Share `evidence-matrix.md` rather than creating another profile or repeating retrieval. A generated resume is a content baseline, not factual proof: follow its source links for consequential ambiguity or new claims.

Keep exact role title, requisition, organization, dates, credentials, ownership, and results consistent across the packet. Let the resume establish breadth and accomplishments; use the letter to explain selected decisions, reasoning, motivation, and relevance. Reuse a project when the letter adds context instead of restating bullets. For several roles at one employer, keep distinct target versions and tailor the evidence case, not just the title.

Save `cover-letter.tex`, `cover-letter.pdf`, and `cover-letter.sources.md` beside the application resume, using an existing handoff's `drafts/` and `revisions/` destinations when applicable. Use the corresponding editable source for another requested format. Preserve previous versions and application status. For paste-ready or plain-text requests, return text without creating files.

## Establish the case and resolve gaps

Read the actual posting and letter instructions: required or optional, questions to answer, word/page limits, accepted file types, and upload versus text field. Follow those instructions over conventions. Read [standards-and-ats.md](references/standards-and-ats.md) when choosing the format, adapting the case for tech versus business, or discussing scanners; reuse that reading within the current task. Recheck changeable vendor behavior or employer requirements when consequential.

Use [retrieve-application-evidence](../retrieve-application-evidence/SKILL.md) for actual gaps. Follow current profile, voice-sample, story, and capability links to the user's decisions and actions. Map important role needs to direct or adjacent evidence; distinguish requirements from preferences and interest from demonstrated readiness. Verify specific organization/team claims against official sources when needed. Research should identify relevant work, not supply flattering company trivia or assumed mission alignment.

Ask only when existing sources cannot resolve a material gap: why this work or employer appeals to the user, personal contribution to a key example, a changed goal, or a consequential content tradeoff. Do not make the user repeat recorded explanations. An inferred fit or old career interest does not establish current motivation. If no personal reason is available, make a supported work-focused case without inventing passion or a lifelong ambition. A required unanswered prompt remains visible as an unresolved gap, not a completed letter.

## Draft and review once

Use [synthesize-application-content](../synthesize-application-content/SKILL.md) for drafting, with this skill owning cover-letter coordination and delivery. Reuse its voice guidance and working brief. When this skill calls synthesis, synthesis returns here for formatting rather than invoking this skill recursively.

Make the role and selection case clear early. Develop a few examples that explain the user's action, an important choice, the result, and its relevance. A concise letter often needs only three or four short paragraphs; choose structure from the actual prompt and substance, not a formula or word quota. Show useful contribution as well as genuine interest. Use ordinary greetings and a short closing; do not pad the page with a second summary or promises of follow-up the user did not make.

Preserve supported confidence, scale, and ownership. Distinguish simulation from physical measurement, planned work from implementation, and directing AI-assisted development from independent coding or model-training proficiency. Explain collaboration when necessary to correct a materially misleading implication, without attaching apologetic disclaimers to every project. Avoid generic enthusiasm, company praise, unsupported self-assessments, keyword inventories, manufactured lessons, and em dashes. Do not use the letter primarily to apologize for early career stage or list missing qualifications.

Use the posting's terminology where evidence supports it. Record important terms and their supporting claims in the shared matrix or letter sidecar; omit unsupported skills instead of inserting them as aspirations to manufacture a match. A term in a cover letter may not be searchable in the same way as a resume. If a supported, important qualification is absent from the resume, flag it or revise it only when resume revision is in scope. Never promise a scanner score, acceptance, or recruiter readership.

Read the complete letter as the recipient before returning to private evidence. What will the recruiter understand and remember? What gives them a specific reason to select this applicant? Identify passages that lose attention, assume missing context, or could describe almost anyone. Check that the letter adds reasoning or context to the resume rather than repeating it. If changing only the employer and role names leaves the case equally convincing, reconsider the chosen evidence and role connection without inventing motivation.

Resolve consequential findings in the actual draft. Recover a missing explanation or select a stronger supported example before polishing sentences; rephrasing a generic claim does not fix it. Then consult source notes to check factual concerns. Preserve supported accomplishments, ownership, accepted wording, and distinctive details. Add caveats only for an actual false or materially misleading implication, not every question a reader might ask. Check whether the revision fixes the underlying objection, not merely whether it sounds smoother.

Apply these reader-impact principles directly or use the shared [review-reader-impact](../review-reader-impact/SKILL.md) workflow, reusing review already completed through synthesis. This substantive review owns final content, claim, voice, and limit checks and any single optional humanizer pass; do not add a second pass merely to invoke a skill. For a substantial paired resume/letter rewrite, use the resume skill's two independent readers on the same recipient-facing packet together, following [independent-readers.md](../review-reader-impact/references/independent-readers.md). One joint review satisfies both workflows; do not commission separate panels for each document. Routine changes need review of affected passages, not another full pipeline. Respect imminent deadlines and explicit restrictions on delegation or testing.

## Format for the destination

For an upload, default to a text-based, one-page PDF plus editable LaTeX source alongside the LaTeX resume. PDF is a practical delivery default, not a universal employer requirement; LaTeX is an authoring choice, not an ATS advantage. Use DOCX or plain text when required or requested. Do not combine the letter with the resume unless instructed, or force a letter into a resume-only upload field.

For an existing letter, locate its source and accepted rendered baseline and preserve effective formatting. For a new letter, locate the resume's actual source and reuse suitable contact-header, font, and link styling. Match the pair without copying resume section headings, bullet macros, tiny type, or compressed spacing into prose. Do not alter the resume to make the letter match. If only the resume PDF exists, use it as a visual reference and disclose source unavailability.

Use a simple one-column business-letter layout, left-aligned paragraphs separated by space, readable 10-12 point body type, and comfortable margins. Prefer 11-12 point when practical. Use one page for ordinary US tech/business letters unless instructed otherwise; do not fill unused space or shrink type to retain low-value prose. Adapt page size and conventions to another requested market. Include the exact role/requisition, appropriate date, verified recipient or ordinary hiring-team salutation, and typed name. Do not invent recipient names, addresses, referrals, or signatures. Do not add a home address or signature image by default.

For LaTeX, fonts, color, links, or an extraction discrepancy, use [pdf-formatting.md](references/pdf-formatting.md). Preserve a working font/compiler setup and judge the exported PDF, not the authoring tool. Keep black body text on white; retain a restrained existing dark accent when matching the resume and check grayscale legibility. Do not impose a blanket color ban or a font whitelist without a relevant requirement.

Keep meaningful text in the ordinary body, with a visually matching contact heading rather than a running header/footer. Prefer one-column paragraphs over layout tables or graphics. Contact links should be black, clickable, and consistently underlined across their visible titles, with email/contact identifiers also visible as text rather than icons alone. An existing resume alignment macro is not by itself a parsing failure or permission to redesign the resume. These are readability and parsing precautions, not proof of an employer's scoring rules.

## Produce and inspect the saved file

Follow the resume skill's editor and installed-compiler approach: distinguish preview from saved PDF export, compile with existing Tectonic (`tectonic --untrusted --outdir APPLICATION_FOLDER cover-letter.tex`) in Claude Code or when export is unavailable, confirm the PDF was written to the application folder, and report unavailable export/compilation plainly. Do not install a compiler or silently replace the chosen renderer. For Word, use the available document skill's render-and-verify workflow.

Render the actual saved PDF after the last edit (in Claude Code, render it to PNG with `pdftoppm -r 150 -png`, or PyMuPDF/pypdfium2 if poppler is missing, view the images with the Read tool, and crop regions at higher resolution for detail checks). Inspect the whole page at reading size and detailed crops of the contact heading, links, body, and closing for readable type, paragraph rhythm, wraps, clipping, spacing, and consistency with the resume. Include a grayscale check when color is used.

When checks are permitted, inspect body reading order, intact words/Unicode characters, name and visible contact text, exact employer/role, page count, and link annotations. Selectable text alone is insufficient. For an extraction discrepancy, compare the source and another available reading method before changing fonts or spacing. Investigate font embedding when relevant to a rendering/extraction problem; embedding alone does not prove usable character mapping. Verify the file opens without a password and meets the actual field's type/size limits.

For a default one-page US Letter PDF, reuse [check_resume_pdf.py](../build-targeted-resume/scripts/check_resume_pdf.py) when automated checks are permitted, passing the expected name/role and only links actually intended for this letter. Its checks cover geometry, expected text, and required links, not all the reading-order or font issues above. Skip the geometry-specific helper for another requested page format. Automated checks do not establish visual quality or universal ATS compatibility. Respect no-tests instructions and do not run project test suites to prepare a letter.

Use the existing [provenance sidecar format](../synthesize-application-content/assets/provenance-sidecar.md) for `cover-letter.sources.md`, linking shared sources rather than duplicating them. Record letter-specific claims, target and resume version, unresolved motivation or ownership, accepted changes, and checks performed. Preserve new reusable self-report through the evidence workflow before saving it as fact. Verify files and local source links, deliver the requested text or source/PDF links, and report material limitations. Do not submit, upload, contact the employer, or change application status without explicit authorization.
