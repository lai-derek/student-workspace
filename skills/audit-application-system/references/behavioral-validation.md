# Behavioral validation of application skills

Use after repeated drafting failures or substantial workflow changes when a realistic trial would add useful evidence. Do not make every wording edit trigger a test suite.

Create an isolated temporary workspace with clearly labeled synthetic or permissioned raw materials: the task, recipient or opportunity information, personal records with ordinary links, relevant existing drafts, and the skills being evaluated. Keep fixtures and generated drafts out of real personal knowledge, application state, and source registrations. Include a materially different case from the failure that motivated the change; copying the same names and connections tests recall rather than transfer.

When delegation is authorized and available, give a fresh agent (in Claude Code, `Agent` with `subagent_type: "general-purpose"`, not `"fork"`) only the task, skills, and raw materials. Do not inherit the authoring chat or disclose the intended connection, suspected failure, expected wording, or grading criteria. A direct replay is usable when independent execution is unavailable, but describe it as such. A plausible model-generated result is still judgment evidence, not a proof of quality.

Inspect the actual reads and output against the original request. Did the workflow find relevant evidence through the records' links, make recipient-specific use of it without inventing facts, preserve the user's distinct motives and real uncertainty, and give related fields different useful jobs? Read the prose for natural movement and recipient-appropriate voice, not exact phrases or a banned-word count. Do not reward shorter text unless the cut improves the result.

Choose a trial that exercises the changed behavior. A workflow revision may need a follow-up asking for a less generic explanation or reporting an imminent deadline; observe whether useful substance survives, the specific objection is resolved, and optional work stops before delivery. Include protected user wording when relevant, even if it contains a phrase the editor might otherwise remove. Do not grade by phrase bans, word-count utilization, or a required repeated theme.

For an iterative failure, follow up with a realistic revision request without prescribing the fix. Compare the versions for preservation of accepted content, diagnosis of the recurring issue, and absence of new claims or generic padding. If the behavior exposes a concrete problem, correct its owner skill and repeat only the affected check. Avoid tuning against one evaluator's taste.

Report the case scope, observed behavior, changes prompted by the result, and limitations. Do not claim a before/after improvement without a comparable baseline. A saved fixture may be retained for reuse when its benefit warrants it; otherwise keep the run temporary. No trial authorizes messages, submissions, or edits to external profiles.
